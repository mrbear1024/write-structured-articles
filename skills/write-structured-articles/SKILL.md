# 结构化文章写作

把文章写成一条清楚的推理路径，让读者知道发生了什么、作者如何判断、凭什么相信，以及接下来能做什么。

## 确定任务

先识别用户需要的交付物：

- 写大纲：输出核心判断和七段式论证骨架。
- 写初稿：从主题与素材发展为完整文章。
- 改写草稿：保留作者的事实、观点和声音，重组结构并补足断裂的推理。
- 评审文章：指出结构、证据、因果、边界和行动建议中的具体缺口；未获要求时不要直接重写全文。

从上下文推断读者、写作目的、篇幅、语气和发布场景。仅当缺失信息会实质改变核心判断时再提问；否则明确合理假设并继续。

## 建立写作底稿

写作前先在内部确定：

1. 读者正在面对的具体变化或问题。
2. 文章承诺帮助读者理解或解决什么。
3. 可以用一句话表达的核心判断。
4. 支持判断的事实、案例与因果链。
5. 判断成立的条件、反例和不确定性。
6. 读者读完后可以复用的框架、方法或动作。

优先使用用户提供的材料。区分事实、他人观点、作者判断和推断；不要虚构数据、案例、引语或来源。涉及时效性事实、精确引用或高风险判断时，先核实来源。

## 按七部分组织

### 1. 开头

用一个具体变化、冲突、场景或问题起笔，并尽快说明它为什么与目标读者有关。避免从宏大趋势、空泛定义或“在当今时代”开始。

### 2. 背景

只补充理解核心判断必需的信息。删除不能改变读者理解或后续推理的背景。

### 3. 核心判断

用一句明确、可争辩、可检验的话说出观点。不要用主题、愿望、口号或两面讨好的表述代替判断。

### 4. 论证

围绕核心判断组织 2 至 4 个论点。每个论点尽量形成以下闭环：

```text
主张 -> 事实或案例 -> 因果解释 -> 对核心判断的支持
```

解释证据为什么支持结论，不要只堆事实。区分相关性与因果性；存在替代解释时主动处理。按推理顺序组织段落，而不是按素材出现顺序拼接。

### 5. 边界

说明判断在什么对象、时间、规模或前提下成立，在哪些情况下可能失效，以及仍有哪些未知。边界不是削弱观点，而是提高观点的可信度和可用性。

### 6. 带走的东西

把判断压缩成读者可复用的框架、检查清单、决策问题或下一步动作。让建议具体到可以开始执行，同时避免超出证据支持范围。

### 7. 结尾

回到开头的问题和文章的核心承诺，收束成读者下一步可以做的事。不要引入未经展开的新论点，也不要只重复摘要。

## 写成文章，而不是模板填空

默认让七部分成为文章的隐性结构，不机械使用“背景”“论证”“边界”等标题。根据体裁合并相邻部分、使用自然过渡，并保持一段只承担一个主要功能。只有用户要求大纲、报告体或显式框架时，才保留结构标签。

优先写具体名词和有动作的动词。删掉空泛铺垫、重复结论、无证据的强断言和不能推动推理的金句。保持用户原有语气；未指定语气时，使用清楚、克制、直接的表达。

## 完稿检查

交付前逐项检查：

- 开头是否同时包含具体问题和读者相关性？
- 背景是否都是理解结论所必需的？
- 核心判断能否用一句话复述，且全文都在支持它？
- 每个主要论点是否有证据和因果解释？
- 事实、判断、推断和不确定性是否区分清楚？
- 是否说明了适用条件、例外或未知？
- 读者是否得到一个可复用框架或可执行动作？
- 结尾是否兑现开头承诺并给出下一步？
- 标题是否准确表达核心价值，而非夸大结论？

若用户要求保存文件，先遵守工作区规则。在 Obsidian 知识库中，将未审核的 AI 文章初稿放入 `.kb/staging/drafts/`；不要把未审核内容直接写入发布目录。
